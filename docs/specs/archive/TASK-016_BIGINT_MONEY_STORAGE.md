## Контекст и проблема

Игроки превысили порог около `9 * 10^18` очков, что упирается в лимит 64-битного знакового `INTEGER` в SQLite. Из-за этого ломаются агрегации и сортировки в `/top`, `/stats`, а часть начислений может перестать увеличивать баланс.

Предыдущий вариант со scale factor и хранением `round(points / 1_000_000)` в `INTEGER` отклонён: он превращает малые суммы в ноль (`50 -> 0`) и ломает текущую игровую экономику. Хранение дробных значений через SQLite `REAL` тоже отклонено из-за потери точности на больших числах.

Требуется сохранить текущую пользовательскую семантику очков: `50` остаётся `50`, ставка `1` остаётся `1`, мелкие выигрыши и проигрыши не исчезают. Одновременно нужно поддержать балансы не ниже `10^24` без переполнения SQLite.

## Requirements

### REQ-016-1: Точное хранение денежных значений

Все денежные значения хранятся без scale factor и без округления.

**Acceptance Criteria:**
- Значение `50` после миграции читается и отображается как `50`.
- Значение `1` после миграции читается и отображается как `1`.
- Значение `10^24` хранится и читается без переполнения.
- В Python денежные значения представлены как `int`.
- SQLite `REAL` не используется для денежных полей.

### REQ-016-2: Схема хранения в SQLite

Денежные колонки переводятся с `INTEGER` на `TEXT`, содержащий каноническое десятичное представление целого числа.

**Acceptance Criteria:**
- Для неотрицательных значений используется строка десятичных цифр без пробелов и разделителей: `"0"`, `"50"`, `"1000000000000000000000000"`.
- Для signed-полей допускается префикс `-`, например `"-10"`.
- Пустые строки, `NULL`, дробные значения и нечисловой текст считаются некорректными данными.
- Код чтения БД валидирует и конвертирует значения через единый money codec.

### REQ-016-3: Область миграции

Мигрировать все поля, хранящие очки, ставки, выигрыши, долги или денежные события.

**Acceptance Criteria:**
- `users`: `balance`, `bid`, `safe_balance`.
- `event_history`: `amount`.
- `ai_credit_sessions`: `reward_amount`.
- `dice_challenges`: `bet_amount`, `initiator_going_debt`.
- `player_debts`: `amount`.
- Heist pot/seed/commission остаются производными от тех же денежных операций; отдельное постоянное хранилище не добавляется, если его нет в текущей схеме.

### REQ-016-4: Money codec

Ввести единый слой конвертации денежных значений между Python и SQLite.

**Acceptance Criteria:**
- Есть функции уровня `money_to_db(value: int) -> str` и `money_from_db(value: object) -> int` или эквивалент.
- `money_to_db` принимает только целые `int` и возвращает канонический `str`.
- `money_from_db` принимает старые `INTEGER` значения и новые `TEXT` значения для совместимости во время миграции.
- Для невалидных значений выбрасывается доменная ошибка или применяется явно задокументированное восстановление в миграции.
- Все DB/repository методы используют codec при чтении и записи денежных полей.

### REQ-016-5: Сортировка и рейтинги

Команды `/top`, `/stats` и любые денежные рейтинги должны корректно работать с `TEXT`-хранением.

**Acceptance Criteria:**
- `/top` сортирует игроков по числовому значению баланса, а не по лексикографическому `TEXT`.
- Для сортировки допускается один из подходов: сортировка в Python после чтения кандидатов, отдельная нормализованная sort key колонка, или фиксированный zero-padded формат для неотрицательных leaderboard-полей.
- Выбранный подход покрыт тестами на значения `9`, `10`, `100`, `10^18`, `10^24`.
- `/stats` не использует SQL `SUM` по `TEXT` без явной безопасной конвертации.

### REQ-016-6: Миграция схемы и данных

Реализовать версионную миграцию SQLite без потери существующих малых значений.

**Acceptance Criteria:**
- Перед изменением схемы создаётся бэкап production БД.
- Миграция создаёт новые таблицы/колонки с `TEXT` денежными полями, копирует данные через безопасную конвертацию и заменяет старые таблицы согласно SQLite-паттерну table rebuild.
- Старое значение `50` мигрирует в `"50"`, а не в `"0"`.
- Старое значение `0` мигрирует в `"0"`.
- Старые отрицательные `event_history.amount`, если они существуют и допустимы по семантике события, сохраняются как signed text.
- Миграция идемпотентна по версии: повторный запуск migration runner не портит уже мигрированную БД.

### REQ-016-7: Обработка сломанных данных

Найти и восстановить некорректные денежные записи до или во время миграции.

**Acceptance Criteria:**
- `NULL` в денежных полях заменяется безопасным значением по контексту (`0` для amount/safe/debt, `starting_points` для отсутствующего user balance, если применимо) с логированием.
- Отрицательный `users.balance` исправляется по правилам текущей экономики: баланс не уходит в минус, долги хранятся отдельно.
- Если значение невозможно интерпретировать, миграция останавливается с понятной ошибкой до изменения таблицы или пишет запись в quarantine/report и применяет явно описанный fallback.
- Для пользователей с подозрительным балансом предусмотрен recovery report с user_id, старым значением, новым значением и причиной.

### REQ-016-8: Изменения приложения

Код бота работает с Python `int` и не знает о строковом формате БД за пределами DB/repository слоя.

**Acceptance Criteria:**
- Handlers принимают пользовательский ввод как обычные очки без масштабирования.
- Сообщения пользователю выводят те же числа, что и до миграции.
- Game config (`starting_points`, лимиты ставок, max debt, heist параметры) остаётся в пользовательских очках.
- AI credit rewards, transfers, safe, dice fights, heist, happy moment и slots используют точные `int` операции.
- Существующие semantic regions для game balance и долгов сохраняются; новая критичная логика помечается регионом `SPEC:TASK-016`.

### REQ-016-9: Тестовое покрытие

Миграция и денежные операции покрыты unit/integration тестами.

**Acceptance Criteria:**
- Unit-тесты money codec: обычные числа, `0`, `1`, `50`, `10^18`, `10^24`, signed amount, невалидные строки.
- Migration-тест на временной SQLite БД со старой `INTEGER` схемой.
- Regression-тест: `/top` сортирует `100` выше `9` и `10^24` выше `10^18`.
- Regression-тест: новый пользователь со `starting_points = 50` получает баланс `50`.
- Regression-тест: ставка `1` и мелкий выигрыш/проигрыш меняют баланс, а не округляются в ноль.

## Goals

**Primary Goal:**  
Устранить переполнение SQLite `INTEGER` для денежных значений, сохранив точную текущую экономику игры и поддержку малых сумм.

**Why This Matters:**
- Игроки не теряют баланс из-за округления.
- `/top` и `/stats` продолжают работать при балансах `10^24+`.
- Миграция не требует немедленного перехода на PostgreSQL.
- Код остаётся проще, чем chunked integer или decimal-scale схемы.

## Design

### Выбранный подход

Использовать SQLite `TEXT` для хранения целых денежных значений, а в Python продолжать работать с `int`.

```text
SQLite TEXT "50"                      -> Python int 50
SQLite TEXT "1000000000000000000000000" -> Python int 10^24
Python int 1                           -> SQLite TEXT "1"
```

### Почему не scale factor

Scale factor `N = 1_000_000` решает верхний предел, но ломает низ экономики: `round(50 / 1_000_000) == 0`. Это неприемлемо для текущей игры, где малые ставки и стартовые балансы являются валидными значениями.

### Почему не REAL

SQLite `REAL` хранит binary float, а не точное decimal-значение. На больших балансах точность шага становится слишком грубой, и мелкие изменения снова могут исчезать. Денежные значения в игре должны быть целочисленными и точными.

### Сортировка `/top`

При `TEXT`-хранении нельзя полагаться на обычный `ORDER BY balance DESC`, если строки не нормализованы: лексикографически `"9" > "100"`. Реализация должна выбрать и закрепить один подход:

1. Читать кандидатов и сортировать в Python по `int(balance)`.
2. Хранить дополнительный sort key для leaderboard-полей.
3. Хранить неотрицательные leaderboard-поля в zero-padded формате фиксированной ширины.

Для минимального риска предпочтителен вариант 1, если размер таблицы `users` остаётся небольшим для группового leaderboard. Если появится проблема производительности, можно перейти к sort key.

### Порядок миграции production

1. Остановить production-бота.
2. Создать файловый backup БД и сохранить его вне рабочей директории git.
3. Выполнить `git push` текущей стабильной версии до миграции.
4. Прогнать migration dry-run на копии production БД.
5. Применить миграцию к production БД.
6. Запустить `./scripts/test.sh` и `./scripts/lint.sh` на версии кода для деплоя.
7. Запустить production-бота.
8. Проверить `/balance`, `/top`, `/stats` и отсутствие traceback в логах.
