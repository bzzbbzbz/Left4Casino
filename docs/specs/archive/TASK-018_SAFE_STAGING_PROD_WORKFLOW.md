**Priority**: HIGH  
**Status**: SPEC_READY  
**Created**: 2026-04-14  
**Assignee**: next-agent

## 📋 Контекст и проблема

Сейчас разработка и эксплуатация бота происходят в одной рабочей копии, что повышает риск:
- случайно выкатывать незавершенный код в прод;
- запускать тесты на боевом токене/чате;
- повредить боевые данные SQLite при экспериментах;
- смешивать hotfix/feature-изменения без контролируемого review.

Нужно внедрить безопасный процесс: отдельная тестовая копия (staging) с отдельным ботом и отдельными секретами, затем перенос изменений в прод только через GitHub (PR + merge + deploy).

---

## 📋 Requirements

### REQ-018-1: Две изолированные рабочие копии через Git Worktree

Организовать два каталога запуска на одном сервере:
- `python-runner-prod` (только стабильная ветка `master`/`main`);
- `python-runner-stage` (ветка для разработки/тестов).

**Acceptance Criteria:**
- staging и prod используют разные директории;
- переключение между средами не требует `git stash`;
- в `README`/документации есть команды создания/обновления worktree.

### REQ-018-2: Два разных Telegram-бота и два набора секретов

Использовать отдельные токены:
- `BOT_TOKEN_PROD` (боевой);
- `BOT_TOKEN_STAGE` (тестовый).

**Acceptance Criteria:**
- токены не хранятся в git;
- для stage и prod используются отдельные файлы конфигурации (`settings.stage.toml`, `settings.prod.toml` или эквивалент);
- запуск каждой среды явно указывает свой `CONFIG_FILE_PATH`.

### REQ-018-3: Изоляция данных (SQLite, state, логи)

Тестовая и боевая среда не должны разделять одну БД и runtime-артефакты.

**Acceptance Criteria:**
- stage и prod имеют отдельные файлы БД;
- исключено одновременное обращение двух процессов к одному `casino.db`;
- логи stage/prod разделены по файлам/юнитам systemd/контейнерам.

### REQ-018-4: Защита от ошибочного использования stage в боевых чатах

Ограничить тестового бота только тестовыми чатами.

**Acceptance Criteria:**
- `settings.stage.toml` содержит `chat_restrictions.allowed_chat_ids` только тестовых групп;
- stage-бот не отвечает в прод-группах;
- prod-бот сохраняет текущие ограничения.

### REQ-018-5: GitHub flow для переноса изменений в прод

Внедрить процесс: feature-ветка -> PR -> CI -> merge -> обновление prod.

**Acceptance Criteria:**
- фиксированная ветка для прод (`master` или `main`, выбрать одну и унифицировать);
- изменения в прод попадают только после merge PR;
- описаны команды обновления prod-копии из origin.

### REQ-018-6: CI-гейт перед merge

Использовать существующие проверки (`lint`, `tests`) как обязательный барьер.

**Acceptance Criteria:**
- PR в прод-ветку запускает workflow `lint.yml` и `test.yml`;
- если в репозитории используется `master`, workflow/branch protection согласованы с этим (без рассинхрона `main` vs `master`);
- в документации указан минимальный набор проверок перед merge.

### REQ-018-7: Стандартизованный деплой в прод

Определить один поддерживаемый путь прод-деплоя (manual pull + restart или CI deploy).

**Acceptance Criteria:**
- описан точный деплой-плейбук для текущей инфраструктуры;
- плейбук включает backup БД перед релизом;
- есть rollback-процедура до предыдущего коммита/бэкапа.

### REQ-018-8: Документированный runbook для команды

Подготовить краткий, повторяемый регламент разработки.

**Acceptance Criteria:**
- в документации есть сценарии: создать feature, протестировать на stage, открыть PR, задеплоить prod;
- есть чеклист безопасности (не коммитить `settings.toml`, `.env`, `*.db`, токены);
- есть чеклист предрелизной валидации.

## 🎯 Goals

**Primary Goal:**  
Сделать процесс разработки бота предсказуемым и безопасным: тесты и эксперименты только в staging, production обновляется только через проверенный GitHub pipeline.

**Why This Matters:**
- снижает риск простоя и потери данных в проде;
- делает релизы воспроизводимыми;
- ускоряет разработку за счет изолированной тестовой среды.

---

## 🚫 Non-Goals

- Миграция с SQLite на PostgreSQL в рамках этой задачи;
- переписывание бизнес-логики бота;
- изменение игровой механики;
- настройка внешнего Kubernetes/сложного оркестратора.

## 📐 Технический дизайн (целевое состояние)

### 1) Структура директорий

Пример:
- `/opt/left4casino/python-runner-prod`
- `/opt/left4casino/python-runner-stage`

Обе директории создаются через `git worktree` из одного origin-репозитория.

### 2) Конфиги среды

В каждой директории хранится свой локальный (неверсионируемый) конфиг:
- `settings.prod.toml`
- `settings.stage.toml`

Запуск:
- prod: `CONFIG_FILE_PATH=/.../settings.prod.toml`
- stage: `CONFIG_FILE_PATH=/.../settings.stage.toml`

### 3) Изоляция SQLite

Минимум:
- отдельный файл БД в каждой worktree.

Желательно:
- явный путь БД в конфиге/env (если будет добавлено в коде) для прозрачной диагностики.

### 4) Git ветки

Рекомендуемый стандарт:
- прод-ветка: `master` (или `main`, но единообразно);
- feature-ветки: `feature/<name>`;
- hotfix-ветки: `hotfix/<name>`.

### 5) CI/CD

Согласовать workflow-триггеры с реальной прод-веткой:
- если прод-ветка `master`, то deploy workflow не должен слушать только `main`;
- required checks: минимум `Lint` + `Tests`.

## ✅ Definition of Done

Задача считается выполненной, когда:
- есть документированный и проверенный сценарий двух сред (stage/prod);
- stage запускается отдельным ботом и не пишет в прод-БД;
- прод обновляется только после PR+CI;
- есть пошаговый deployment и rollback runbook;
- в репозитории нет утечки секретов и runtime-артефактов.

## 🧪 Проверка и приемка

### Smoke для staging
- stage-бот стартует с `settings.stage.toml`;
- отвечает только в тестовом чате;
- пишет данные в отдельную stage-БД.

### Smoke для production
- prod-бот стартует с `settings.prod.toml`;
- продолжает работать в боевых чатах;
- stage-действия не влияют на prod-данные.

### GitHub flow
- PR из `feature/*` в прод-ветку запускает CI;
- merge доступен только после green checks;
- после merge прод-копия обновляется и успешно перезапускается.

---

## ⚠️ Риски и меры

- **Риск:** случайный запуск prod-токена в stage.  
  **Мера:** отдельные config-файлы + явный `CONFIG_FILE_PATH` в unit/service.

- **Риск:** повреждение прод-БД при деплое.  
  **Мера:** обязательный backup до перезапуска.

- **Риск:** автодеплой не срабатывает из-за несоответствия ветки (`main`/`master`).  
  **Мера:** унифицировать ветку во всех workflow.
